# BlockSize feed internals and the current latency path

Scope: what BlockSize Capital's upstream market-data feed looks like today, as seen from (a) the public Matrix API documentation and (b) the local Agentic Payments repository (`/Users/johannfocke/Documents/Antigravity/Agentic Payments`, read-only), so that a DoubleZero Edge publisher architecture can consume it. Repo facts cite `path:line`; web facts cite URLs. No secrets were read or printed; the API key is only described as present (env `BLOCKSIZE_API_KEY`).

Correction to the brief: the production API host is `data.blocksize.capital`, not `matrix.blocksize.capital`. `matrix.blocksize.capital` is the customer portal and hosts the documentation (`/api-docs`, `/api-docs.json`). Both names resolve to the same Google Cloud anycast address (see the hosting section).

## Q1. Which WebSocket / JSON-RPC methods exist, with parameters, response fields and timestamps? Is there a server-side timestamp per update?

### Takeaway
The Matrix API is JSON-RPC 2.0 over WebSocket (`wss://data.blocksize.capital/marketdata/v1/ws`) and HTTP (`https://data.blocksize.capital/marketdata/v1/api`). Streaming methods are `vwap_subscribe`, `fixedvwap_subscribe`, `bidask_subscribe`, `state_subscribe`, `trade_subscribe` (each with an `_unsubscribe`), pushing notifications named `vwap`, `fixedvwap`, `bidask`, `state`, `trade`. Every row carries a timestamp (`ts` in ms for VWAP, `ts` in microseconds for bid/ask, `timestamp` in seconds for state), but the VWAP `ts` is the exchange-provided time of the last trade used, and there is no separate "server sent at" field, so upstream latency can only be measured as exchange-trade-time to local-receipt-time.

### Inferences
- A per-update "server publish time" does not exist in the documented schemas. For VWAP the only timestamp is the exchange-provided time of the last trade in the aggregate, so (local receipt time − `ts`) measures exchange→BlockSize→batching→network→client as one number; it cannot separate BlockSize's internal latency from the exchange's. For bid/ask the doc only says "The UTC timestamp in microseconds" without saying whether it is exchange or aggregation time; the microsecond resolution suggests it is set by BlockSize's aggregator rather than copied from an exchange feed (most exchanges publish ms). This is an inference, not documented.
- `time_now` returns whole seconds, so it is too coarse for clock-offset estimation against millisecond latencies; an Edge publisher would need NTP/PTP-disciplined clocks on both ends or a BlockSize-side change to add a send timestamp.
- Because the repo's HTTP bid/ask read pulls the full `bidask_getSnapshot` (all ~2,700 instruments) per call, its measured HTTP latency overstates what a filtered WebSocket subscription would see (see Q2 numbers).

### Gaps
- The doc does not type the `state_subscribe`/`state_pool` fields ("untyped in schema") nor say whether `aggregated_state_price` is in quote units or USD; only examples exist.
- Whether `bidask` `ts` is exchange time or aggregator time is undocumented.
- No raw captured production payloads are saved in the repo (grep for `agg_bid_price`/`aggregated_state_price` in output/, scratch/, reports/, analysis/ found nothing), so the above shapes rest on the public doc plus repo test fixtures and the client's parsing code.

## Q2. What is the publish cadence of VWAP and bid/ask updates, and where does the "250 ms" figure come from? What latency figures exist?

### Takeaway
The public doc states that `vwap`, `bidask` and `trade` notifications "will be sent in 250 millisecond batches", "immediately" when a price changes, and are re-sent after 60 s without change; `state` is immediate on change; `fixedvwap` is once per day at 00:00 UTC. The 250 ms figure therefore most plausibly originates from this batching interval (and from a third-party listing's "<250ms latency" claim), not from a measured end-to-end latency. The repo's only measured numbers are HTTP round trips from Austin (median 173 ms for `vwap_latest`, 270 ms for `bidask_getSnapshot`) and a gateway p95 of 620 ms.

Updates will immediately be sent when the price of an asset has changed and re-sent if the price has remained unchanged for 60 consecutive seconds." — [Matrix API docs JSON, vwap_subscribe](https://matrix.blocksize.capital/api-docs.json)
- Bid/ask cadence: identical wording ("250 millisecond batches", immediate on change, re-sent after "60 consecutive seconds" unchanged). — [Matrix API docs JSON, bidask_subscribe](https://matrix.blocksize.capital/api-docs.json)

### Inferences
- "250 ms" in the team's conversation is almost certainly the documented batching interval (worst-case added delay before an update leaves BlockSize), possibly blended with the Datarade "<250ms latency" line. Nothing in the repo or public docs documents a measured 250 ms end-to-end figure. Note that a 250 ms batch plus ~150-250 ms HTTP/WS transit from the US gives 400-500 ms typical end-to-end for a US consumer today, while a European consumer colocated with the backend would see roughly batching (0-250 ms) plus a few ms.
- Cadence is event-driven within fixed 250 ms batch windows (not a fixed-interval tick): an instrument appears in a batch only if its price changed, except for the 60 s heartbeat re-send. An Edge publisher therefore sees at most 4 updates/s per instrument and at least one every 60 s.
- The ~165 ms warm-connection TTFB for a trivial rejection is consistent with the backend sitting in Europe behind Google's anycast edge (see Q6), and with the audit medians (173 ms for small `vwap_latest` responses; 270 ms for the ~2,700-row `bidask_getSnapshot`). The difference between the two upstream methods is mostly payload size.

### Gaps
- No measurement anywhere in the repo of WebSocket notification latency (exchange `ts` to receipt). The only WebSocket consumers are the 24h VWAP and state caches, which do not record receipt-vs-`ts` deltas.
- No documented SLA, p50/p99 or jitter figures from BlockSize itself.
- Railway's deployment region for the gateway is not recorded in the repo (grep of docs/, Procfile for region names found nothing), so the production gateway→BlockSize hop cannot be estimated from repo evidence.

## Q3. Instrument universe, and which instruments are the natural first Edge feed?

### Takeaway
As of the 6 October 2026 audit the upstream catalogs list 7,234 real-time VWAP tickers (but only 2,447 live within 5 minutes), 2,762 bid/ask instruments (2,626 ok; 167 of them tokenized/equity-like, 7 FX, 4-5 metals), and 230 AMM state instruments (220 ok, Solana and EVM pools). The pairs that are fresh on both VWAP and bid/ask with many CEX venues (BTC, ETH, SOL against USD/USDT/USDC/EUR) are the obvious first Edge feed; metals and FX are bid/ask-only and, per the public plan table, "Non-crypto Instruments" are an Enterprise-plan feature.

# Low-latency market-data publisher design and the competitive crypto price-feed set (as of 16 October 2026)

Scope: engineering and competitive notes to inform a cross-venue crypto price feed (VWAP + top-of-book from ~110 exchanges) published over DoubleZero Edge multicast. Figures carry the date of the source where it is stated. Primary specs and vendor docs preferred; secondary coverage flagged as such. The Nasdaq MoldUDP64 spec PDF was downloaded but its text could not be machine-extracted (font-encoded); where a detail from it is stated from memory rather than from fetched text, it is marked "[recalled, verify]". The Eurex T7 R15.0 EOBI manual text was extracted and is quoted directly. Binance's live Terms of Use page serves no body text to automated clients; its data-use clause is cited from a 2023 archive via a secondary source.

## Key Question 1: What concrete message-layout and recovery design should a new Edge publisher adopt, and what do existing Edge feeds (Hyperliquid, Kalshi, Binance) use?

### Takeaway
DoubleZero publishes an open, Apache-2.0 wire-format family (`malbeclabs/edge-feed-spec`) and a Rust publisher/codec/recorder reference (`malbeclabs/edge-multicast-ref`); every venue on Edge (Hyperliquid, trade.xyz, Kalshi, Binance, Phoenix) uses this same family, so a new publisher should not design its own frame but implement an existing spec (Top-of-Book) and, for a derived VWAP, either the Midpoint feed's "derivation-explicit" pattern or a new sibling spec merged into `edge-feed-spec` first. The family borrows the exchange-grade patterns (per-channel u64 sequence, reset counter, heartbeats, snapshot+delta on a separate port, fixed-size little-endian messages, in-band reference data) but deliberately omits re-request/retransmission and A/B arbitration; recovery is "continuous in-band snapshot" only.

### Cited Findings

**DoubleZero Edge wire-format family (primary spec)**
- The `edge-feed-spec` repo (public since 12 Oct 2026, Apache-2.0) holds eight specs: Top-of-Book & Trades, Midpoint, Market-by-Order, Market-by-Price, Order-Intent, Reference Data Distribution, Perp Stats, and a Source ID Registry; "Every feed's frame header carries a `Schema Version` byte equal to its spec's MAJOR version"; within a major line "changes are additive only". Five feeds carrying the 130-byte `InstrumentDefinition` are at 3.0.0; Midpoint is at 1.0.0. — [edge-feed-spec README](https://github.com/malbeclabs/edge-feed-spec/blob/main/README.md)
- Design principles of the Top-of-Book feed (v3.1.0): little-endian; fixed-size messages ("No variable-length fields, no repeating groups"); schema-versioned; multicast-native ("One frame per UDP datagram"); numeric `u32` instrument IDs on the data path with strings only in reference data; every price message carries a `u16` Source ID; domain-agnostic. — [Top-of-Book spec](https://github.com/malbeclabs/edge-feed-spec/blob/main/top-of-book/spec.md)
- Frame header is 24 bytes: Magic `u16` (0x445A "DZ"), Schema Version `u8`, Channel ID `u8`, Sequence Number `u64` ("Monotonically increasing per channel, starting from 0. Resets to 0 when `Reset Count` changes. Used for gap detection."), Send Timestamp `ts_ns` (u64 ns since epoch), Message Count `u8` (1–255), Reset Count `u8` ("Incremented each time the publisher resets the channel"), Frame Length `u16`. Application message header is 4 bytes: Type `u8`, Length `u8` (max 255), Flags `u16` (bit 0 = snapshot vs incremental). — [Top-of-Book spec](https://github.com/malbeclabs/edge-feed-spec/blob/main/top-of-book/spec.md)
- Maximum frame size is 1,232 bytes "to leave room for GRE encapsulation headers used by the DoubleZero network's last-mile delivery"; a `Quote` is 60 bytes (84 with header for a single-message frame); 20 quotes + header = 1,224 bytes. — [Top-of-Book spec](https://github.com/malbeclabs/edge-feed-spec/blob/main/top-of-book/spec.md)
- `Quote` (0x03, 60 B) fields: Instrument ID u32, Source ID u16, Update Flags u8 (bit 0 bid updated, bit 1 ask updated, bit 2 bid gone, bit 3 ask gone), Source Timestamp ts_ns ("Timestamp from the originating venue"), Bid/Ask Price as `i64` with per-instrument implied exponent, Bid/Ask Qty `u64`, Bid/Ask Source Count u16. `Trade` (0x04, 52 B) carries aggressor side, trade flags, source timestamp, price, qty, venue trade ID, cumulative volume. `Heartbeat` (0x01, 16 B) "Sent every N seconds when there is no other traffic"; `EndOfSession` (0x06, 12 B); `Liquidation` (0x08, 48 B) MUST be in the same frame as its `Trade`. — [Top-of-Book spec](https://github.com/malbeclabs/edge-feed-spec/blob/main/top-of-book/spec.md)
- Two-port channel model: each channel is "one multicast group on two destination ports" — `mktdata` (Quote, Trade, Heartbeat, EndOfSession) and `refdata` (InstrumentDefinition, ManifestSummary, StrikeInterval); a cold-start subscriber MUST bind both. Rationale: reference-data traffic is too small to justify a second multicast group's IGMP/provisioning cost. — [Reference Data supplement](https://github.com/malbeclabs/edge-feed-spec/blob/main/reference-data/spec.md)
- In-band reference data replaces an offline catalog or replay service: publisher MUST retransmit every active `InstrumentDefinition` within a "definition cycle period" (recommended 30 s), paced evenly (no bursts), and emit `ManifestSummary` (Manifest Seq u16 + Instrument Count u32) at a "manifest cadence" (recommended 1 s); subscriber is `ready()` when it holds `expected_count` definitions tagged with the latest Manifest Seq. Worst-case cold start = M + T ≈ 31 s at recommended settings. Bandwidth for 1,000 instruments ≈ 35 kbps. — [Reference Data supplement](https://github.com/malbeclabs/edge-feed-spec/blob/main/reference-data/spec.md)
- Channel reset is signalled only by the frame header: "To reset the channel, the publisher increments `Reset Count` in the frame header and resets `Sequence Number` to 0 … Subscribers detect the reset by comparing `Reset Count` against their last-seen value and discard all cached state". — [Reference Data supplement](https://github.com/malbeclabs/edge-feed-spec/blob/main/reference-data/spec.md)
- Depth feeds (Market-by-Price v3) add a third `snapshot` port and three independent sequence series: per-port channel seq (gap detection per stream), a dense per-instrument `u32` delta seq (never reset at snapshot boundaries, so `≤ last_applied` is unambiguously a duplicate and `> last_applied + 1` a gap), and a `SnapshotBegin.Anchor Seq` equal to the `mktdata` sequence at capture time ("This snapshot is the exact state … after every delta … with `Sequence Number ≤ Anchor Seq`"). — [Market-by-Price spec](https://github.com/malbeclabs/edge-feed-spec/blob/main/market-by-price/spec.md)
- Recovery is snapshot-only: "An instrument in `gap` status is recovered by the next `SnapshotBegin` for it … Worst-case recovery time equals one snapshot cycle period. The spec provides no in-band mechanism to request an expedited snapshot." Publishers emit snapshots round-robin within a configured snapshot cycle period (operator-tuned; worked example T = 15 s gives ~4.5 Mbps on the wire for 500 instruments / 250k levels). Publishers MUST emit `Heartbeat` when idle, "recommended 1 s", and MUST emit `BatchBoundary` when the upstream applies level changes atomically. — [Market-by-Price spec](https://github.com/malbeclabs/edge-feed-spec/blob/main/market-by-price/spec.md)
- Publishers whose upstream (e.g. a WebSocket) has no replay "carry the whole recovery burden themselves": on an upstream gap the publisher MUST re-read the upstream book and issue `InstrumentReset` (Reason 3 = UpstreamGap), then an out-of-cycle snapshot. — [Market-by-Price spec](https://github.com/malbeclabs/edge-feed-spec/blob/main/market-by-price/spec.md)
- Subscriber-side crossed-book monitoring is "observability, not control flow" and does not trigger re-bootstrap. Delta buffers MUST be bounded (worked case: 30 M messages ≈ 1.4 GB at T = 60 s). — [Market-by-Price spec](https://github.com/malbeclabs/edge-feed-spec/blob/main/market-by-price/spec.md)
- The Midpoint feed (Magic 0x4D44) is the family's template for a derived price: a 40-byte `Midpoint` with `Method` u8 (1 BBO mid, 2 micro-price, 3 depth-weighted mid, 4 last-trade fallback, 255 custom "documented out of band"), `Quality Flags` (stale, one-sided, crossed/locked, synthetic) and three timestamps (venue Book Timestamp, publisher Compute Timestamp, frame Send Timestamp) so "Compute − Book is publisher-side processing lag. Send − Compute is publisher egress lag." Principle 8: "A derived price without provenance is a number without a contract." — [Midpoint spec](https://github.com/malbeclabs/edge-feed-spec/blob/main/midpoint/spec.md)
- The Perp Stats feed (Magic 0x4450) is a "sibling cadence feed" for REST-polled derived state (funding, mark, oracle, OI) with the principle "REST-poll data belongs on a REST-cadence feed, not co-located with matching-engine events", and fixed-exponent `rate` (10⁻¹²) and `notional` (10⁻²) types. — [Perp Stats spec](https://github.com/malbeclabs/edge-feed-spec/blob/main/perp-stats/spec.md)
- Source ID Registry: `Source ID` identifies a matching engine, not a venue. Assigned: 1 Hyperliquid native perps, 2 Phoenix, 3 Kalshi, 4–5 Setai, 6 Binance USD-margined futures, 7 XYZ (HIP-3 DEX on Hyperliquid), 8 Binance Spot, 9 Binance coin-margined futures. Venue codes follow TradingView's data-coverage names. — [Source ID Registry](https://github.com/malbeclabs/edge-feed-spec/blob/main/sources/spec.md)
- The reference repo states the transport: "DoubleZero delivers data as GRE-encapsulated UDP multicast. The kernel handles GRE de-encapsulation, so applications see clean UDP"; tunnel interface `doublezero1` has MTU 1476; an optional XDP `gre-decap` program strips GRE on the physical NIC. Publisher crates: `dz-edge-core` (headers, sequencing), `dz-edge-tob`, `dz-edge-refdata`, `dz-edge-mbp`, `dz-publisher-metrics`; recorder uses `AF_PACKET` by default "so a datagram the recorder's own socket would have lost to receive-queue overflow is still in the archive". — [edge-multicast-ref README](https://github.com/malbeclabs/edge-multicast-ref/blob/main/README.md)
- Onboarding rule: for "a new feed type" the first step is "Specify it in `edge-feed-spec` and get that merged … a publisher that decided one of these for itself is the defect class this whole design exists to prevent"; a venue adapter implements `dz_adapter_core::Adapter` (`poll_listings`, `on_connected`, `on_payload`, `snapshot`), and all crates are pulled by git tag (v0.6.0), "there is nothing on crates.io". Publisher config has `snapshot_cycle = "5s"` for depth feeds and `id_allocation`. — [BRINGING-UP-A-FEED.md](https://github.com/malbeclabs/edge-multicast-ref/blob/main/BRINGING-UP-A-FEED.md)
- `doublezero-edge-connect` is a one-command bridge that decodes the "little-endian fixed-size datagrams", drives the reference-data state machine and re-serves JSON over `ws://host:8081` "with four latency timestamps for end-to-end measurement"; requires GRE (IP protocol 47), raises `net.core.rmem_max`, and verifies an on-chain access pass before connecting. — [doublezero-edge-connect README](https://github.com/malbeclabs/doublezero-edge-connect)

**Exchange-grade patterns to compare against**
- Nasdaq MoldUDP64: "a lightweight layer on UDP that lets listeners detect missed packets and re-request them"; each packet sent once regardless of listener count; re-request goes to a server when a sequence gap is seen and "The response is a standard Downstream Packet unicast back to the requester", so one socket serves multicast and retransmission; heartbeats "typically transmitted once per second and contain the next expected Sequence Number" (Moss UDP sibling spec). — [Nasdaq MoldUDP64 spec PDF](https://m.nasdaqtrader.com/content/technicalsupport/specifications/dataproducts/moldudp64.pdf); [Nasdaq Moss UDP](https://NASDAQTrader.com/content/technicalsupport/specifications/dataproducts/mossudp.pdf)
- A MoldUDP64 implementation header confirms "All structures use network byte order (big-endian)" and `EOS_COUNT = 0xFFFF` as the end-of-session marker. [recalled, verify against the PDF: Downstream header = 10-byte Session + 8-byte Sequence Number + 2-byte Message Count; each message block = 2-byte length + payload; heartbeat = Message Count 0; Request packet = Session + Sequence Number + 2-byte Requested Message Count.] — [b2bits MoldUDP64 Messages.h](https://corp-web.b2bits.com/ITCH/moldudp64_2_messages_8h.html)
- Japannext's MoldUDP64 variant uses end-of-session packets in place of heartbeats and has listeners send re-request packets after a gap; conventions on whether SeqNum is "current" or "next expected" differ by venue. — [JNX MoldUDP64 1.02](https://www.japannext.co.jp/pub_data/pub_onboarding/JNX_MoldUDP64_Specification_1.02.pdf); [MOON ATS MD spec](https://www.otcmarkets.com/files/MOON-ATS-MD-Specification.pdf)
- CME MDP 3.0: packets carry a per-channel sequence number ("increments with each packet, and resets weekly") and a send timestamp "in nanoseconds since the Unix epoch"; one packet holds multiple SBE-encoded messages; "Incremental Feeds A and B send the same packets" for arbitration; Market Recovery feeds publish snapshots "for all books with activity since the start of the week" at "a constant, configurable packets-per-second rate"; TCP Recovery (Historical Replay) "suited to small-scale recovery only, with data available for the last 24 hours". — [OnixS CME MDP3 glossary](https://ref.onixs.biz/cpp-cme-mdp3-handler-guide/glossary.html); [CME MDP 3.0 Dissemination](https://cmegroupclientsite.atlassian.net/wiki/spaces/EPICSANDBOX/pages/457222936/MDP+3.0+-+Dissemination)
- CME guidance: "all book updates in the latest Market Data Incremental Refresh message must be processed before the order book can be considered valid"; for MBP-only UDP systems CME recommends Market Recovery with Natural Refresh as primary recovery. — [CME MDP 3.0 Recovery Services](https://cmegroupclientsite.atlassian.net/wiki/x/Fz1CGw)
- Vendor gap handlers do not declare loss on first out-of-order packet: OnixS waits "a predefined time interval" or until "new incoming packets have sequence numbers greater than a certain threshold". — [OnixS packet gap detection](https://ref.onixs.biz/cpp-cme-conflated-udp-handler-guide/group__packet-gap-detection.html)
- A/B feeds may packetize identically-sequenced messages differently, so "parsing packets before arbitration" is required (Exegy patent). — [USPTO 10872078](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10872078)
- Eurex T7 EOBI (T7 Release 15.0 EOBI Manual v1, text extracted from the PDF): messages are "fixed-length binary encoded" with "little endian byte order" integers of 1/2/4/8 bytes and defined NoValue sentinels (e.g. 0xFFFFFFFF for a 4-byte unsigned); the packet header "allows receiving applications to identify identical packets between service A and service B … by a simple memory comparison on the first 12 bytes of a T7 EOBI datagram containing the ApplSeqNum"; in the PacketHeader "MsgSeqNum is always filled with 0xFFFFFFFF"; "packets have contiguous sequence numbers per EOBI channel (service A and service B)" so `ApplSeqNum` detects both duplicates and gaps; EOBI channels are not shared between partitions; on loss on both Live-Live services, "recovery on the participant side can be achieved by recovering the order book information via the T7 EOBI snapshot channel"; snapshot messages carry `LastMsgSeqNumProcessed` and "Any incoming incremental messages with a sequence number higher than the LastMsgSeqNumProcessed received in the snapshot message should be applied to the order book after the full snapshot message is processed"; the manual has dedicated Heartbeats (4.15), Recovery (4.16) and Timestamps (ch. 5) sections. Databento summarises EOBI as the "Full market by order (MBO) feed for latency-sensitive users" and Eurex's EMDS manual notes EOBI is the exception to FAST encoding; a Xetra circular lists separate A/B snapshot and incremental multicast addresses per partition. — [T7 R.15.0 EOBI Manual PDF](https://www.cashmarket.deutsche-boerse.com/resource/blob/5409230/2887252247af7d3ba65ccee909ecfb58/data/T7_R.15.0_%20EOBI_Manual_Version_1.pdf); [Databento T7 glossary](https://databento.com/microstructure/t7); [Eurex EMDS manual](https://www.eurexchange.com/resource/blob/2059782/39975e1efdbe3b7dd4262488ef55c62a/data/EMDS_Underlying_Ticker_Manual_v.8.11.pdf); [Xetra circular on EOBI A/B addresses](https://www.deutsche-boerse-cash-market.com/dbcm-en/newsroom/circulars-newsletters/Xetra-circulars-mailings/T7-B-rse-Frankfurt-production-environment-Change-of-partition-ID-and-EOBI-MDI-multicast-addresses-for-instruments-currently-on-partition-4-4581524)
- Timestamps: Databento's PCAPs "include our PTP receive timestamps, which allow users to measure timestamp deltas … in sub-millisecond environments"; Linux `SO_TIMESTAMPING` offers hardware RX/TX timestamps whose raw value "is not tied to system time", requiring `phc2sys` to discipline the system clock from the NIC PHC. — [Databento intraday PCAP](https://databento.com/blog/intraday-market-data-pcap); [Linux timestamping.txt](https://elixir.bootlin.com/linux/v3.15.4/source/Documentation/networking/timestamping.txt); [RHEL PTP guide](https://docs.redhat.com/en/documentation/red_hat_enterprise_Linux/6/html/deployment_guide/s1-using_ptp)
- Binary encoding options: SBE's reference implementation covers "Java, C++, Golang, C#, and Rust". — [simple-binary-encoding mirror](https://github.com/FPanda/simple-binary-encoding)

### Inferences
- A new Edge publisher should implement the existing Top-of-Book spec (per-venue BBO/trades with real Source IDs 6/8/9 for Binance etc.) and model the composite VWAP on the Midpoint feed's pattern — a fixed-size message with a `Method` byte, `Quality Flags`, venue/compute/send timestamps — rather than inventing a frame. Because a cross-venue VWAP has no single matching engine, the Source ID model (one engine per ID) does not fit a composite; either a new "Composite" spec with a constituent mask / count field, or a reserved Source ID for "DoubleZero composite", needs to be agreed in `edge-feed-spec` before publishing (the repo's process makes this a hard prerequisite).
- Edge's recovery philosophy differs from exchange feeds: no unicast re-request (MoldUDP64), no TCP replay (CME), no A/B arbitration. For a stateless VWAP/TOB feed this is acceptable — the next update is the recovery — provided updates are frequent or a periodic "snapshot-flagged" full refresh (Flags bit 0) is emitted every few seconds; for any stateful depth product, the spec already defines the snapshot-port round-robin and the publisher must size `snapshot_cycle` against level count.
- The spec family already answers the SBE-vs-custom question: Edge uses hand-laid fixed-size little-endian structs with length-prefixed skipping instead of SBE; adopting SBE would make a publisher non-conformant with `dz-conformance`. SBE/FlatBuffers remain relevant only for internal or non-Edge distribution.
- Clock discipline matters for the three-timestamp provenance model: the composite's `Compute Timestamp` and `Send Timestamp` are only meaningful if the publisher host is PTP/PHC-disciplined; venue `Source Timestamp`s from exchange WebSockets are millisecond-granular and of unknown accuracy (see KQ2).

### Gaps
- The MoldUDP64 PDF text could not be extracted; its byte-level field sizes above are from memory and should be checked against the PDF before being written into a spec. EOBI heartbeat interval and timestamp-field semantics (manual sections 4.15 and 5) were not read in detail.
- The Binance-on-Edge multicast groups, feed codes, pricing and licensing basis were not found (docs.malbeclabs.com/binance/ exists in navigation but returned 404 to the fetcher).
- No independent latency measurements of any Edge feed were found; all performance claims are DoubleZero's or its partners'.
- Whether DoubleZero runs redundant publisher instances per channel in production (the MBP spec supports "Redundant Channel Instances" keyed by source IP) is not documented publicly.

## Key Question 2: What latency can an aggregator realistically achieve (ingest from exchange WS in-region, aggregate, publish over private fiber) and where does the remaining time go?

### Takeaway
In-region WebSocket ingest from Binance in AWS Tokyo measures ≈4 ms median / ≈13 ms p99 from exchange timestamp to packet capture (Deltix, June 2023); aggregation compute is negligible by comparison; the dominant remaining term is geography — one-way fiber from Tokyo is ≈35 ms to Singapore, ≈72 ms to New York, ≈100 ms to London/Frankfurt (Hats Network inter-PoP RTTs, 16 Oct 2026, halved) — and a 110-venue composite is as stale as its farthest constituent (Coinbase/Kraken are US/EU-hosted, Bybit Singapore, OKX Hong Kong). A private network's edge over public internet on these routes is reported as ~10–20 ms at p50 with larger tail gains, not an order of magnitude.

### Inferences
- Budget for a Tokyo-ingested Binance composite delivered to a Tokyo subscriber: ≈4 ms (p50) exchange→ingest, <1 ms aggregation if the publisher is single-threaded and allocation-free, ≈1–3 ms metro multicast delivery (based on Glassnode's 0.7 ms co-located WS and GRE overhead), so ≈5–8 ms p50 and ≈15–20 ms p99 is realistic; this is dominated by the exchange's own WS fan-out jitter (Deltix p99/p50 ratio ≈3.3×).
- For a subscriber in another metro the budget is geography plus the above: Singapore ≈+35 ms, New York ≈+72 ms, Frankfurt/London ≈+98–102 ms one-way on backbone fiber; a private network can shave roughly 10–20 ms off public-internet p50 on these routes and more at p99 (per DZ-adjacent reports), but cannot beat the ≈10 ms/1,000 km floor.
- A 110-venue composite inherits the farthest venue's inbound hop: Coinbase (US-hosted) data reaches a Tokyo aggregator ≈72 ms after Coinbase emits it; Kraken (EU) ≈100 ms; Bybit (Singapore) ≈35 ms; OKX (Hong Kong) ≈23 ms. A single-site aggregator therefore produces a composite whose constituents are 5–100 ms stale in a venue-dependent way. Two mitigations follow from the Edge specs: publish per-venue TOB feeds from regional ingestion sites (Tokyo, Singapore, New York, Frankfurt/London) with venue `Source Timestamp`s intact, and let subscribers or a second-stage publisher compose; or compute the VWAP per region and label it (the Midpoint `Method`/`Quality Flags` pattern) so staleness is explicit.
- Exchange `Source Timestamp`s are millisecond-granular and depend on the exchange's clock; the Deltix method (exchange timestamp vs PTP/NTP-disciplined receive time) is the right instrumentation for the publisher's own health metrics (`dz_publisher_*`), and the three-timestamp model lets subscribers separate exchange lag from publisher lag from wire lag.

### Gaps
- No post-2023 packet-level WebSocket latency study for Binance, and none at all for Bybit, OKX, Coinbase or Kraken WebSockets; the 2026 figures found are REST TTFB (includes TLS and server processing) or WS ping RTT, not message-arrival-vs-exchange-timestamp.
- No public measurement of DoubleZero Edge end-to-end market-data latency (publisher Send Timestamp to subscriber receive) in any metro.
- Exact Chicago RTTs on a backbone-grade source and exact DoubleZero metro-to-metro RTTs were not found; DoubleZero's `doublezero latency` CLI (referenced in its docs) is the primary tool but requires network access.
- Exchange matching-engine-to-WebSocket-egress time (inside the exchange) is not observable from outside and is folded into the Deltix figures.

### Inferences
- Freshness is not the binding constraint for HIP-3 crypto perps: the chain ingests oracle updates every ≥2.5 s and clamps mark moves to 1 % per update, and Hyperliquid's own crypto oracle is a 3 s weighted median of CEX mids. Pyth Pro's 1–50 ms `real_time` channel is already far faster than the chain consumes. A "fresher than Pyth" pitch has little marginal value on-chain; it has value off-chain for the deployer's pusher (deciding what to submit) and for market makers quoting on HIP-3 books, who do care about tens of milliseconds.
- The differentiator the incident record supports is pricing-engine quality and transparency: constituent-level VWAP with explicit venue set, size weighting, cross-venue deviation filters, stale/one-sided/synthetic quality flags, and bounds vs. a reference — exactly the Midpoint-spec provenance model generalized. A composite from 110 venues with published methodology competes on "would have rejected the Nextrade print", not on 1 ms.
- Price-wise, a Tokyo-ingested Edge VWAP/TOB feed at Edge-like tiers ($900–$1,500 per feed per metro) sits between Pyth Starter ($500, 1 s) and Pyth Pro ($2,500+, 1 ms) — but Pyth Pro bundles signed on-chain payloads and 120+ first-party publishers (market-maker quotes, equities), which a CEX-derived composite does not replicate. Non-crypto coverage (equities, FX) is where Pyth/Chainlink/RedStone compete for HIP-3 deployers of RWA perps; a crypto-only composite does not address that segment.
- Pyth's own data path is CEX-adjacent (publishers include market makers; infra in Tokyo); from Europe its freshness advantage over raw Binance was ≈8 ms in the one independent sample, which suggests any Tokyo-hosted feed, including an Edge composite, will show the same geography-dominated profile to non-Tokyo subscribers.

## Key Question 4: What are the data-licensing constraints on redistributing centralized-exchange market data, and how do Kaiko, Amberdata, CoinAPI and Tardis handle them?

### Takeaway
Every major exchange's terms grant only a personal/internal, revocable, non-sublicensable licence and reserve redistribution for written consent or a separate data-licensing agreement — OKX (API Agreement §9.4, 28 Jul 2026) says so explicitly for public endpoints, Coinbase's Market Data Terms (7 Aug 2026) bar building end-user applications and route commercial use through "authorized redistribution partners", Kraken's Global Terms (6 Oct 2026) prohibit commercial exploitation and third-party apps without consent, and Binance's terms (2023 archive) list "data feeds and streaming services" among commercial uses requiring written consent. Vendors handle this by signing exchange redistribution contracts (Kaiko: 26 exchanges; Amberdata: Coinbase and CME; Tardis: listed as a Coinbase redistribution partner) or by refusing raw redistribution entirely (CoinAPI). A 110-venue redistributed feed therefore needs exchange-by-exchange agreements or must be positioned as a derived product; DoubleZero's own Binance feed shows the exchange route is negotiable but its terms were not disclosed.

### Inferences
- Re-publishing per-venue top-of-book from Binance, OKX, Coinbase, Kraken or Bybit over Edge without a written agreement would conflict with each exchange's current terms; OKX is the clearest (public endpoints included, separate licence required), Coinbase next (no end-user applications; redistribution via partners), Kraken and Binance by broad "no commercial exploitation / no data feeds without consent" language. The 110-exchange ambition multiplies this: the long tail of venues has terms of similar shape but no redistribution program at all.
- A composite VWAP is a "Derived Work" under Coinbase's definition (indexes, benchmarks) and likely under others; derived-data licences exist in TradFi and are what Kaiko sells for "regulated financial products", so a composite is more licensable than raw TOB but still not licence-free.
- Practical routes: (1) become an exchange-authorized redistributor venue-by-venue (the Kaiko/Amberdata model; Binance appears to negotiate such deals through its market-data team); (2) partner with DoubleZero, which already has a Binance arrangement and a publisher revenue-share model, so that the exchange is the publisher of record and the composite is a derived product on top; (3) license inputs from a redistributor whose contract permits derived-data redistribution (Kaiko states this; CoinAPI explicitly does not).
- A clean separation helps: publish exchange-attributed raw TOB only where a licence exists, and publish the composite (with constituent counts but not constituent prices) everywhere.

## Key Question 5 (objective part d): Which Rust crates and public examples are relevant to building a multicast publisher?

### Takeaway
The only public, maintained Rust multicast market-data publisher is DoubleZero's own `edge-multicast-ref` (codec, publisher runtime, adapter trait, AF_PACKET recorder, XDP receiver; Apache-2.0; pulled by git tag, not on crates.io); around it, `socket2` 0.6.5 provides the multicast socket options, `quanta` 0.13.0 the TSC clock, `crossbeam` 0.8.5 the lock-free queues, `pcap` 2.5.0 capture, `aya` 0.14.0 / `xdp-socket` for XDP/AF_XDP, and `sbe_gen` 0.7.3 or `ironsbe` 0.4.2 if SBE is wanted; `tokio-uring` (0.5.0, May 2024) is young and does not document UDP.

### Cited Findings
- `edge-multicast-ref`: Rust crates `dz-edge-core` ("Datagram and message headers, sequencing, receive-side walk, decimal conversion"), `dz-edge-tob`, `dz-edge-refdata`, `dz-edge-mbp`, `dz-publisher-metrics`, plus `dz-adapter-core`, `dz-publisher-runtime`, `dz-ingress-core` (feature `websocket`) and `dz-ingress-fix`; recorder crates with `AF_PACKET` default capture, kernel receive timestamps and drop accounting; `rust/xdp-receiver` and `gre-decap` XDP program; Go parsers as the cross-language check; golden wire vectors in `testdata/golden/`. Dependencies pinned by git tag v0.6.0. — [edge-multicast-ref README](https://github.com/malbeclabs/edge-multicast-ref/blob/main/README.md); [BRINGING-UP-A-FEED.md](https://github.com/malbeclabs/edge-multicast-ref/blob/main/BRINGING-UP-A-FEED.md)
- `dz-conformance` validates a publisher against the spec's rule catalog from live multicast or pcap/pcapng replay with a CI-friendly exit code; covers TOB, Midpoint, MBO, MBP and the Reference Data supplement. — [edge-feed-spec README](https://github.com/malbeclabs/edge-feed-spec/blob/main/README.md)
- `socket2` 0.6.5: `join_multicast_v4` (IP_ADD_MEMBERSHIP with interface address), `join_multicast_v4_n` (by index or address), `leave_multicast_v4`, `set_recv_buffer_size` (SO_RCVBUF), plus `set_reuse_port`, `set_multicast_if_v4`, `set_multicast_loop_v4`, `set_multicast_ttl_v4`, `join_ssm_v4`, `bind_device`. — [docs.rs socket2 Socket](https://docs.rs/socket2/latest/socket2/struct.Socket.html)
- `quanta` 0.13.0 (2026-09-27): TSC-based high-speed clock with OS fallback, "the cost of `Clock::now` is on par `Instant::now` from the stdlib, if not better"; TSC only on x86/x86_64. — [docs.rs quanta](https://docs.rs/crate/quanta/latest)
- `crossbeam` 0.8.5 (2026-09-05): `ArrayQueue` (bounded MPMC), `SegQueue`, channels, epoch GC, `CachePadded`, `Backoff`. — [docs.rs crossbeam](https://docs.rs/crate/crossbeam/latest)
- `tokio-uring` 0.5.0 (2024-05-27): "still very young", requires recent kernels (5.4 fails, 5.11 works), safe APIs for only some io_uring ops; UDP not mentioned on the crate page. — [docs.rs tokio-uring](https://docs.rs/crate/tokio-uring/latest)
- `pcap` 2.5.0 (2026-08-15): libpcap bindings, live capture, BPF filters, savefiles, injection; needs `cap_net_raw,cap_net_admin` on Linux; hardware timestamp types not mentioned. — [docs.rs pcap](https://docs.rs/crate/pcap/latest)
- `aya` 0.14.0: pure-Rust eBPF library, no libbpf/bcc, BTF support, async with tokio; XDP/AF_XDP specifics not on the overview page. `xdp-socket` 0.1.4: "simple and transparent Rust implementation of AF_XDP sockets" with `TxSocket`/`RxSocket`; `afxdp` wraps libbpf-sys. — [docs.rs aya](https://docs.rs/aya/latest/aya/); [docs.rs xdp-socket](https://docs.rs/crate/xdp-socket/latest); [docs.rs afxdp](https://docs.rs/crate/afxdp)
- `sbe_gen` 0.7.3 (2026-04-27): SBE XML → zero-copy Rust types via `zerocopy`; groups, var data, composites, builders; self-described "work-in-progress", single owner. `ironsbe` 0.4.2: broader SBE implementation whose transport crate covers "TCP, UDP unicast/multicast, shared memory IPC". — [docs.rs sbe_gen](https://docs.rs/crate/sbe_gen/latest); [docs.rs ironsbe](https://docs.rs/crate/ironsbe/0.4.2)
- `moldudp` 0.1.1: MoldUDP64 client that "automatically re-requests dropped/missing packets and supports multiple re-request servers"; consumer must reorder by sequence; validates only ≥20-byte length. — [docs.rs moldudp](https://docs.rs/crate/moldudp/0.1.1)
- `pyth-lazer-protocol`: Rust crate for the Pyth Lazer/Pro wire protocol (useful for consuming Pyth as a comparison input). — [docs.rs pyth-lazer-protocol](https://docs.rs/pyth-lazer-protocol)
- Kernel-bypass background: AF_XDP sockets (XSK) give "full or partial kernel bypass"; zero-copy mode "requires driver support", copy mode works with any driver; one write-up describes an XDP pre-filter on known price-feed multicast groups before the XSK. — [ebpf-docs AF_XDP](https://docs.ebpf.io/linux/concepts/af_xdp/)

### Inferences
- Build the publisher on DoubleZero's crates rather than from scratch: `dz-publisher-runtime` already owns sequencing, Reset Count, 1,232-byte datagram packing, refdata cadence and Prometheus metrics, and a venue only supplies an `Adapter`. A VWAP feed would need a new codec crate + spec (the "new feed type" path), reusing the Midpoint pattern.
- Keep the hot path synchronous and allocation-free (crossbeam SPSC/ArrayQueue between WS decode threads and a single sequencing/send thread; `quanta` for Compute/Send timestamps); `tokio-uring` is not mature enough to justify on a UDP send path, and standard `sendmmsg` via `socket2`/`libc` is the conservative choice. Hardware timestamps for health metrics need `SO_TIMESTAMPING` + `phc2sys`, which `pcap` does not expose; the DZ recorder's AF_PACKET path is the model.
- SBE is unnecessary for Edge conformance; it is relevant only if the same engine also serves non-Edge clients.

### Gaps
- No benchmark comparing kernel sockets vs AF_XDP for a Rust multicast publisher was found; the DZ reference repo contains an XDP receiver but publishes via kernel sockets.
- `edge-multicast-ref` crates are not on crates.io and version history beyond tag v0.6.0 was not reviewed; API stability is unknown.
- No open-source Rust ITCH/MoldUDP64 *publisher* or simulator was found (only the `moldudp` client).

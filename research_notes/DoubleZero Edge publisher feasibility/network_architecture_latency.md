# DoubleZero (2Z) network: physical and software architecture, connection modes, latency and costs (state as of 16 October 2026)

Scope note: figures from the public DoubleZero data API (`https://data.doublezero.xyz/api/...`) were pulled on 2026-10-16 at 19:14 UTC and are a point-in-time snapshot. The DoubleZero marketing site (doublezero.xyz) returns HTTP 403 to generic fetchers; its pages were read with a browser user agent. Everything not labelled "verified" below should be re-checked with the team's own `doublezero latency` run before any purchasing decision.

## Key question 1: Connection modes (IBRL vs multicast), client software, how a host attaches, and access requirements

### Takeaway
A host joins DoubleZero by installing the `doublezero` package (daemon `doublezerod` + CLI `doublezero`), which opens a GRE tunnel (IP protocol 47) from the host's own public IPv4 to the nearest DoubleZero Device (DZD) and runs BGP (TCP/179 on 169.254.0.0/16 link-locals) over it; IBRL unicast rides interface `doublezero0`, multicast rides a second GRE interface `doublezero1` with PIM. Access is gated on-chain by an "access pass" tied to a DoubleZero ID (Solana keypair) and client IP: validators self-serve via the Passport flow, Edge market-data subscribers buy seats in USDC/2Z, and everyone else (RPC, trading firms wanting IBRL, private multicast) is still permissioned via a form/Telegram. No 2Z staking is required to use the network.

### Cited Findings
- Setup requirements: "x86_64 server with a public IP address (no NAT)"; OS Ubuntu 22.04+, Debian 11+, Rocky/RHEL 9+; root/sudo; validators must install "directly on your validator host, not in a container"; Testnet and Mainnet-Beta are separate networks chosen at install — [DoubleZero docs: Setup](https://docs.malbeclabs.com/setup/)
- Install (mainnet-beta, Debian/Ubuntu): `curl -1sLf https://dl.cloudsmith.io/public/malbeclabs/doublezero/setup.deb.sh | sudo -E bash` then `sudo apt-get install doublezero`; RPM: `.../setup.rpm.sh` then `sudo yum install doublezero`; testnet uses the `doublezero-testnet` Cloudsmith repo. Install adds an enabled systemd unit `doublezerod` — [DoubleZero docs: Setup](https://docs.malbeclabs.com/setup/)
- Identity and discovery: `doublezero keygen` (writes `~/.config/doublezero/id.json`), `doublezero address`, `doublezero latency` (lists DZ devices with pubkey, name, IP, min/max/avg latency, reachability), `doublezero status`, `doublezero disconnect` — [DoubleZero docs: Setup](https://docs.malbeclabs.com/setup/)
- Firewall: GRE is IP protocol 47; BGP is tcp/179 on 169.254.0.0/16 over `doublezero0`; e.g. `sudo iptables -A INPUT -p gre -j ACCEPT`, `sudo iptables -A INPUT -i doublezero0 -s 169.254.0.0/16 -d 169.254.0.0/16 -p tcp --dport 179 -j ACCEPT` — [DoubleZero docs: Setup](https://docs.malbeclabs.com/setup/)
- Daemon flags (Prometheus example): `/usr/bin/doublezerod -sock-file /run/doublezerod/doublezerod.sock -env testnet -metrics-enable -metrics-addr localhost:2113` via `/etc/systemd/system/doublezerod.service.d/override.conf`; metrics include `doublezero_build_info` and `doublezero_session_is_up` — [DoubleZero docs: Setup](https://docs.malbeclabs.com/setup/)
- Client repo description: "a daemon which handles the establishment of tunnels into DoubleZero and a CLI for establishing smartcontracts and interacting with the local daemon"; monorepo dirs `client/{doublezero,doublezerod}`, `controlplane`, `smartcontract`, `telemetry`, `api`, `offchain`, `solana`, `sdk`; Rust + Go; local devnet simulates DZDs with Arista cEOS images — [github.com/malbeclabs/doublezero client README](https://github.com/malbeclabs/doublezero/blob/main/client/README.md); [DEVELOPMENT.md](https://github.com/malbeclabs/doublezero/blob/main/DEVELOPMENT.md)
- Latest monorepo release tags: `monitor/v0.44.0`, `funder/v0.44.0`, `geoprobe-agent/v0.44.0`, `internet-latency-collector/v0.44.0` published 2026-10-02; repo pushed 2026-10-16 — [GitHub API releases](https://api.github.com/repos/malbeclabs/doublezero/releases)
- IBRL connect (validator): `doublezero connect ibrl`; "IBRL mode uses the machine's existing public IP, so validator clients do not need a restart"; after ~1 minute `doublezero status` shows `up`, `Tunnel src` = public IPv4; BGP routes appear via `ip route` as `... via 169.254.0.68 dev doublezero0 proto bgp`; one primary + up to three backup machines share one DoubleZero ID — [DoubleZero docs: IBRL publish/connect validator](https://docs.malbeclabs.com/solana/ibrl/publish/)
- Validator access pass ("Passport") flow: `doublezero-solana passport find-validator -u mainnet-beta`; `doublezero-solana passport prepare-validator-access -u mainnet-beta --doublezero-address <ID> --primary-validator-id <ID> --backup-validator-ids <IDs>`; `solana sign-offchain-message service_key=<DZ_ID>,backup_ids=<IDs> -k <identity-keypair.json>`; `doublezero-solana passport request-validator-access -k <keypair> -u mainnet-beta --primary-validator-id <ID> --backup-validator-ids <IDs> --signature <SIG> --doublezero-address <DZ_ID>`; identity must hold >= 1 SOL and be in gossip + leader schedule; the Sentinel agent then creates the access pass; also open udp/44880 on `doublezero0` — [DoubleZero docs: IBRL publish](https://docs.malbeclabs.com/solana/ibrl/publish/)
- Non-validator IBRL ("Permissioned / RPC"): "User onboarding is currently permissioned for non-validators and RPCs"; fill the onboarding form, then watch Telegram; provide DoubleZeroID, validator/node ID and public IPv4; "There may be fees associated with Permissioned User usage in the future"; connect with `doublezero connect ibrl` — [DoubleZero docs: Permissioned / RPC](https://docs.malbeclabs.com/solana/ibrl/subscribe/)
- Multicast connect (generic): `doublezero connect multicast --publish <feed>`, `--subscribe <feed>`, both flags combinable and multi-valued (`--subscribe feed1 feed2`); status example shows "User type: Multicast; tunnel ID 515; tunnel net 169.254.3.58/31; Groups: P:mg02; access pass: Prepaid (MAX); tunnel type: GREOverDIA"; publishers get a DoubleZero IP (e.g. 198.18.0.1) distinct from Tunnel Src; subscriber-only users show a blank DoubleZero IP (use `doublezero user list --client-ip <ip>`) — [DoubleZero docs: Other multicast](https://docs.malbeclabs.com/reference/other-multicast/)
- Edge subscriber multicast: `doublezero connect multicast --subscribe-feed solana-shreds-full` (feed-code subscriptions need client >= v0.35.0); multicast arrives on `doublezero1`, not `doublezero0`; firewall must allow GRE, BGP tcp/179 on `doublezero1`, PIM outbound (`-p pim`), the feed's UDP ports on `doublezero1`, and udp/44880 on `doublezero0`; "The private key for your DoubleZero ID must be on the machine that receives shreds" — [DoubleZero docs: Subscribe to shreds](https://docs.malbeclabs.com/solana/edge/subscribe/); [Binance page](https://docs.malbeclabs.com/binance/)
- Transport as seen by the host: "Physical NIC: Eth → Outer IP → GRE → Inner IP → UDP → payload"; `doublezero1@NONE: <POINTOPOINT,NOARP,UP,LOWER_UP> mtu 1476 ... link/gre <host public IP> peer <DZD IP> inet 169.254.10.233/31`; an optional XDP program `gre-decap` strips GRE inline on the NIC so socket apps can receive without the tunnel interface — [edge-multicast-ref README](https://github.com/malbeclabs/edge-multicast-ref)
- Edge Connect (Docker bridge, recommended by DZ for market data): `curl -fsSL https://get.doublezero.xyz/connect | bash` (testnet: `/connect-testnet`); container bundles `doublezerod` + CLI, runs `--network host` with `NET_ADMIN`/`NET_RAW`/`/dev/net/tun`, loads `tun`/`ip_gre`, raises `net.core.rmem_max`, verifies the access pass on-chain "for `0.0.0.0` (the any-IP wildcard) nor for the host's public IP" before installing, then runs `doublezero connect multicast` with up to 4 retries; serves normalized JSON over `ws://host:8081`; config only via env vars (`DZ_SECRET`, `DZ_ENV`, `DZ_FEEDS`, `DZ_CHANNELS`, `DZ_CLIENT_IP`, ...); host `doublezerod` and the container cannot both bind udp/44880 — [doublezero-edge-connect README](https://github.com/malbeclabs/doublezero-edge-connect)
- Tenants: `doublezero config set --tenant shelby` then `doublezero connect ibrl` (Shelby is testnet-only today) — [DoubleZero docs: Shelby](https://docs.malbeclabs.com/shelby/)
- Access-pass on-chain schema (from the public data lake catalog): `dz_access_passes_current` columns include `owner_pubkey, type_tag, client_ip, user_payer, last_access_epoch, connection_count, status, mgroup_pub_allowlist, mgroup_sub_allowlist, flags, feed_seats`; devices carry `max_users, max_unicast_users, max_multicast_subscribers, max_multicast_publishers, reserved_seats` — [data.doublezero.xyz/api/catalog](https://data.doublezero.xyz/api/catalog)
- Economic model: payments "in 2Z, USD or USDC. All USD or USDC payments are programatically converted to 2Z, a portion (currently 10%) is then burned"; validator access fee "was removed entirely" — [DoubleZero Q2 2026 Token Holder Update, 18 Aug 2026](https://doublezero.xyz/journal/doublezero-q2-2026-token-holder-update)
- Architecture components: DoubleZero Daemon (host), Activator (IP allocation/state changes), Controller (renders device config from smart-contract events), Agent (on DZDs, polls Controller), DZD (physical enclosure), DZX exchanges "in major metropolitan areas where contributor links are bridged together" — [DoubleZero docs: Architecture](https://docs.malbeclabs.com/reference/architecture/)

### Inferences
- A market-data publisher that is not a Solana validator cannot self-serve onto the network today: both IBRL (permissioned form) and a dedicated multicast group ("reach out to discuss pricing") go through the Foundation/Malbec Labs. Subscribing to existing Edge feeds is the only fully self-serve path (web form + USDC escrow + CLI).
- Because the tunnel is GRE from the host's own public IP with no NAT, cloud instances behind 1:1 NAT (AWS elastic IP) work only if the provider passes protocol 47 and the instance accepts packets for the NAT'd address (hence AWS "disable ENI source/dest check"); CGNAT or shared-IP hosting will not work.
- The `doublezero1` GRE MTU of 1476 and the 1,232-byte datagram cap in the Edge spec mean no jumbo frames for users; the contributor-side MTU 2048 requirement is internal to the fabric.

### Gaps
- No public document states per-user bandwidth caps for IBRL users; the only quantified caps are per multicast group (`max_bandwidth`, see Q5) and per-device user counts.
- The versioning of the client is inconsistent in public sources: docs require "v0.35.0 or later" of the `doublezero` client, GitHub tags on the monorepo are `v0.8.0` (root) and `*/v0.44.0` (components). Could not verify the current client package version from the Cloudsmith repo.
- "doublezero" vs "doublezero-solana" package split: `doublezero-solana` (Passport, `shreds pay`) is a separate apt package/repo (github.com/malbeclabs/doublezero-solana, last pushed 2026-09-07); its CLI reference was not fetched.

## Key question 2: Topology — metros, PoPs, contributors, links and inter-metro latency (incl. Tokyo to Chicago / New York / London / Frankfurt)

### Takeaway
As of 16 Oct 2026 the mainnet-beta has 31 metros (27 with devices), 90 devices in 65 facilities, 154 links (101 WAN, 53 DZX; 77 at 100 Gbps, 73 at 10 Gbps), 8.745 Tbps aggregate, 15 contributors and 2,168 users. Link telemetry gives direct inter-metro RTTs of Tokyo–Chicago 120.8 ms (one 10 Gbps Cumberland/DRW link), Tokyo–Frankfurt 133.9 ms (one 10 Gbps InFiber link), Tokyo–LA 98.7 ms, Tokyo–Seattle 81.8 ms, Tokyo–Singapore 64.4 ms; shortest multi-hop paths give Tokyo–New York ~137.5 ms and Tokyo–London ~144.8 ms RTT. ### Inferences
- `latency_us` on links is almost certainly RTT between the two DZDs (Frankfurt–Tokyo 133.9 ms is consistent with a ~67 ms one-way great-circle fiber path). One-way propagation on DoubleZero from Tokyo is therefore roughly: Chicago ~60 ms, Washington/New York ~68–69 ms, Frankfurt ~67 ms, London ~72 ms, Singapore ~32 ms, Hong Kong ~24 ms. Add host-side GRE/tunnel processing (sub-millisecond) and the DZD hop counts above.
- The Tokyo–Chicago and Tokyo–Frankfurt direct links are single 10 Gbps contributions from one contributor each (Cumberland/DRW, InFiber); loss of either falls back to multi-hop paths (Tokyo→Seattle→Chicago ≈ 121 ms RTT via 100 Gbps links; Tokyo→LA→Chicago ≈ 137 ms) so the fabric is redundant but not latency-equivalent.
- Versus the Hats public-internet matrix, DoubleZero's Tokyo–Frankfurt 134 ms vs ~193 ms public (~30% better) and Tokyo–London 145 vs ~203 ms are the big wins; Tokyo–New York (137.5 vs ~145 ms) is only marginally better because the public path already uses trans-Pacific + US routes. Treat the public figures as indicative only.

### Gaps
- DoubleZero publishes no per-corridor public-internet comparison in a machine-readable form that I could fetch (the `dz_vs_internet_latency_comparison` table exists in the catalog but `/api/performance/*` returned the SPA HTML shell, not JSON). The Path Calculator UI must be used interactively.
- No third-party measurement of Tokyo–Chicago over DoubleZero exists; Figment/Solana Compass/RPC Fast give only percentage or Frankfurt-local numbers.
- Whether `latency_us` is RTT or one-way is not documented on the API; inferred from magnitude.

## Key question 3: Hardware and hosting — who houses DZDs, can cloud/bare-metal boxes connect, FPGA story, bandwidth caps

### Takeaway
DZDs are Arista 7280CR3A switches paired with AMD V80 FPGAs (4U, ~4 kW per site) placed by contributors mostly in Equinix, Digital Realty/Interxion, Telehouse, CoreSite, CyrusOne and AT TOKYO facilities; users need no hardware beyond an x86-64 Linux host with a public IPv4 that can send/receive GRE (bare metal preferred; AWS works with ENI source/dest check disabled; Cherry Servers and Latitude host DZDs in their own DCs). The FPGA "edge filtering" feature is documented as not yet functional; the multicast groups are rate-capped at 50 Mbps–1 Gbps each.

### Inferences

## Key question 5: Multicast specifics — groups, publish/subscribe commands, allocation, public group list, packet-size and rate limits

## Key question 7: What can DoubleZero realistically do to the team's ~250 ms end-to-end market-data latency?

### Takeaway
Network propagation on DoubleZero from Tokyo is ~60 ms one-way to Chicago, ~68 ms to New York/Washington, ~67 ms to Frankfurt and ~72 ms to London (half of the measured link RTTs), with microsecond jitter; DoubleZero's own Binance feed is ingested in Tokyo and multicast at these propagation times plus publisher encode time. A 250 ms end-to-end figure is therefore dominated by things other than the wire (exchange WebSocket fan-out, TCP/TLS, serialization, retries), and moving to DoubleZero can bring the network component to roughly 60–75 ms one-way intercontinental, or single-digit ms intra-metro, but only if the publisher sits in a DoubleZero metro (Tokyo for Binance) and subscribers run native multicast or Edge Connect on DZ-attached hosts.

### Cited Findings
- Binance on Edge: "Data is ingested from Binance in Tokyo" and republished as UDP multicast; quote timestamps µs (spot, gateway send time) / ms (USD-M, matching engine time); message types Heartbeat, InstrumentDefinition, Quote, Trade, EndOfSession, ManifestSummary — [DoubleZero docs: Binance](https://docs.malbeclabs.com/binance/); "A DoubleZero publisher connects to Binance's market data and republishes it in the same wire format as every other feed on Edge" — [doublezero.xyz/binance](https://doublezero.xyz/binance)
- Edge Connect adds "four latency timestamps for end-to-end measurement" to each JSON message — [doublezero-edge-connect README](https://github.com/malbeclabs/doublezero-edge-connect)
- Measured DZ link RTTs out of Tokyo: Chicago 120.8 ms, Frankfurt 133.9 ms, LA 98.7 ms, Seattle 81.8 ms, Singapore 64.4 ms, Hong Kong 48.3 ms; computed shortest paths New York 137.5 ms, London 144.8 ms, Amsterdam 139.8 ms — [data.doublezero.xyz/api/dz/links?limit=500](https://data.doublezero.xyz/api/dz/links?limit=500)
- Public-internet comparison points (non-DZ): Tokyo–Frankfurt ~193 ms, Tokyo–London ~203 ms, Tokyo–New York ~145 ms RTT — [Hats Network](https://hatsnet.io/docs/network/latency)
- Last-mile to a DZD from a same-metro host in the docs example: 1.84 ms avg (`dz-ny7-sw01`) up to 14.52 ms (`dz-tor1-sw01` from New York) — [IBRL publish docs](https://docs.malbeclabs.com/solana/ibrl/publish/)

### Inferences
- Option A (publish through DoubleZero Edge as a venue): the team's publisher would implement the `dz_adapter_core::Adapter` trait and run `dz-publisher-runtime` on a Tokyo (or other metro) host with a publisher-allowlisted access pass; subscribers anywhere on DZ receive at ~propagation + sub-ms. Expected Tokyo→Chicago one-way ≈ 60–62 ms, Tokyo→Frankfurt ≈ 67–70 ms, Tokyo→London ≈ 72–75 ms, intra-Tokyo ≈ 1–3 ms. Onboarding is bespoke (contact Foundation/Malbec), not self-serve.
- Option B (own infrastructure using DZ as transport): IBRL unicast between the team's own hosts in DZ metros is possible today only as a permissioned user; a private multicast group is quote-priced. Latency equals Option A's propagation; the advantage is control over format and subscriber set, the cost is permissioning and bespoke pricing.
- Option C (subscribe to DZ's existing Binance feed, $100/month per engine per machine): the cheapest way to benchmark immediately; the team can compare Edge Connect timestamps against its own 250 ms pipeline before committing to publishing.
- The 250 ms figure cannot be reduced below the ~60–75 ms intercontinental one-way floor by any network; the remaining ~175+ ms is in the application path and will be eliminated only by redesigning the publish path (binary UDP, no per-subscriber TCP), which Edge's wire format forces anyway.

### Gaps
- No DoubleZero source states the ingest-to-wire latency of its Binance publisher (exchange WebSocket → multicast); it must be measured with the Edge Connect timestamps.
- No published one-way (as opposed to RTT) measurements, and no third-party verification of the Tokyo→US/EU corridor figures beyond the API telemetry read here.

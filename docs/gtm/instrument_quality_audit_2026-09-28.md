# Blocksize Instrument Quality Audit

Audit date: 2026-09-28 (local); run started 2026-09-28T23:46:56+00:00 UTC

Methodology:

- Enumerated every instrument per service through `BlocksizeClient` (`list_vwap_instruments`, `bidask_instruments` catalog split by the client's fx/metal/equity heuristics, `list_fx_instruments`, `list_metal_instruments`, `list_state_instruments`).
- Probed each symbol once with the matching client call (`get_vwap_latest`, `get_bidask_snapshot`, `get_fx_rate`, `get_metal_price`).
- State was probed the way `/v1/state/{pair}` serves it: the `state_subscribe` websocket aggregate first, then the `state_instruments` + `state_pool` HTTP fallback. Each state row's `notes` column records which source answered. The HTTP path reports the pool's last on-chain `block_time`, which is legitimately old for quiet pools, so it is not evidence of a stale live feed.
- Concurrency 8, per-call timeout 30s, stale threshold 300s.
- Freshness is judged from the raw upstream payload. When the payload carries no timestamp the client substitutes the current time, so those rows are classified as `zero_or_missing_values` (timestamp_source = synthesized) rather than trusted as fresh.
- Read-only: no writes to the upstream API, no product code changed. No secrets or authentication material were printed or written.
